# Testing & Benchmarks

This document contains testing and benchmark results for `kyn-vdf` across different environments.

## Browser WASM Testing

`kyn-vdf` can be compiled natively to WebAssembly (`wasm32-unknown-unknown`) using `wasm-pack`, enabling full in-browser verification of Wesolowski VDF proofs without relying on C++ or `libgmp`.

### Methodology

The benchmark takes a known 100-iteration test vector generated by the official Chia C++ prover. The verification math is run continuously in an asynchronous loop within the browser to test stability, memory management, and average execution time.

### Results

The following benchmark was measured by compiling the project with `wasm-pack build --target web --release` and running the verification equation in a tight loop.

**Environment:**
- **Browsers:** Mozilla Firefox & Chromium (Google Chrome / Brave)
- **Target:** WebAssembly (`wasm32-unknown-unknown`)

**Firefox Benchmark:**
```text
Result: ✅ VALID
Total time: 295.68 seconds
Average time per verification: 295.68 ms
(Measured over 1000 runs)
```

**Chromium Benchmark:**
```text
Result: ✅ VALID
Total time: 280.31 seconds
Average time per verification: 280.31 ms
(Measured over 1000 runs)
```

**Mobile Chrome (Android/iOS) Benchmark:**
```text
Result: ✅ VALID
Total time: 409.30 seconds
Average time per verification: 409.30 ms
(Measured over 1000 runs)
```

### Analysis
An average of **~280-295 ms on desktop** and **~409 ms on a mobile device** over 1,000 continuous runs is an exceptional result for a pure WebAssembly implementation running in a browser. 

1. **Stability & Thermals:** The constant execution over 1,000 rounds proves there are no memory leaks in the Rust-to-JS WASM bindings or the underlying `num-bigint` operations. The mobile device exhibited no UI lagging and no thermal throttling (heating), proving the WASM footprint is lightweight enough for mobile light clients.
2. **Real-World Viability:** Because Wesolowski verification scales at $\mathcal{O}(\log T)$, this sub-half-second verification time remains mostly constant regardless of how many iterations ($T$) the prover performed. This makes it perfectly fast enough for both desktop and mobile web wallets to instantly verify blocks without impacting the user experience.

### True $\mathcal{O}(\log T)$ Reality Check (T = 100,000)

When benchmarking with a low iteration count like $T=100$, the exponent $r = 2^T \pmod B$ is simply $2^{100}$. Because $2^{100}$ is much smaller than the 264-bit Fiat-Shamir prime $B$, the verification equation computes $x^r$ using only 100 squarings. 

For a true "reality check" representing real-world consensus proofs, we benchmarked a proof where $T=100,000$. Here, $r$ wraps modulo $B$, resulting in a full 264-bit exponent. This forces the verifier to perform the maximum theoretical work (~264 squarings for $x^r$).

**Firefox Desktop Benchmark (T = 100,000):**
```text
Result: ✅ VALID
Total time: 442.30 seconds
Average time per verification: 442.30 ms
(Measured over 1000 runs)
```

**Chromium Desktop Benchmark (T = 100,000):**
```text
Result: ✅ VALID
Total time: 381.56 seconds
Average time per verification: 381.56 ms
(Measured over 1000 runs)
```

**Mobile Chrome (Android/iOS) Benchmark (T = 100,000):**
```text
Result: ✅ VALID
Total time: 568.76 seconds
Average time per verification: 568.76 ms
(Measured over 1000 runs)
```

**Scaling Analysis:**
The total number of squarings required went from ~364 (at $T=100$) to ~528 (at $T \ge 264$). This $1.45\times$ increase in mathematical work is perfectly reflected in the execution time increasing from ~295ms to ~442ms. From this point forward, whether $T=100,000$ or $T=10,000,000$, the verification time will remain entirely flat at ~442ms in WASM!

## Cross-Platform Native Benchmarking

To measure the true "speed limit" of your processor without the overhead of the WebAssembly abstraction layer or UI framework FFI bindings (Tauri/Flutter), you can run the pure Rust `native_bench` directly.

### Desktop Native (x86_64 / ARM64)
To test raw performance on your desktop machine:
```bash
cargo run --release --example native_bench
```

### Mobile Native (ADB Shell on Android)
To test the raw performance of an Android ARM64 processor without the overhead of Flutter, you can cross-compile the Rust binary and execute it directly in the Android shell.

1. **Add the Android NDK Target:**
   ```bash
   rustup target add aarch64-linux-android
   ```

2. **Compile the Benchmark:**
   *(Ensure you have the Android NDK and `cargo-ndk` installed)*
   ```bash
   cargo ndk -t arm64-v8a build --release --example native_bench
   ```

3. **Push to Phone & Execute:**
   ```bash
   adb push target/aarch64-linux-android/release/examples/native_bench /data/local/tmp/
   adb shell chmod +x /data/local/tmp/native_bench
   adb shell /data/local/tmp/native_bench
   ```
