# Testing & Benchmarks

This document contains testing and benchmark results for `kyn-vdf` across different environments.

## Browser WASM Testing

`kyn-vdf` can be compiled natively to WebAssembly (`wasm32-unknown-unknown`) using `wasm-pack`, enabling full in-browser verification of Wesolowski VDF proofs without relying on C++ or `libgmp`.

### Methodology

The benchmark takes a heavy 100,000-iteration ($T=100,000$) test vector generated by the official Chia C++ prover. In this scenario, the exponent $r$ wraps modulo $B$, resulting in a full 264-bit exponent. This forces the verifier to perform the maximum theoretical mathematical work (~264 squarings for $x^r$), representing a true "reality check" for real-world consensus proofs.

The verification math is run continuously in an asynchronous loop within the browser to test stability, memory management, and average execution time.

### Results

The following benchmark was measured by compiling the project with `wasm-pack build --target web --release` and running the verification equation in a tight loop.

**Firefox Desktop Benchmark:**
```text
Result: ✅ VALID
Total time: 442.30 seconds
Average time per verification: 442.30 ms
(Measured over 1000 runs)
```

**Chromium Desktop Benchmark:**
```text
Result: ✅ VALID
Total time: 381.56 seconds
Average time per verification: 381.56 ms
(Measured over 1000 runs)
```

**Mobile Chrome (Android/iOS) Benchmark:**
```text
Result: ✅ VALID
Total time: 568.76 seconds
Average time per verification: 568.76 ms
(Measured over 1000 runs)
```

### Analysis
An average of **~381-442 ms on desktop** and **~568 ms on a mobile device** over 1,000 continuous runs is an exceptional result for a pure WebAssembly implementation running inside a browser sandbox. 

1. **Stability & Thermals:** The constant execution over 1,000 rounds proves there are no memory leaks in the Rust-to-JS WASM bindings or the underlying `num-bigint` operations. The mobile device exhibited no UI lagging and no thermal throttling (heating), proving the WASM footprint is lightweight enough for mobile light clients.
2. **Real-World Viability:** Because Wesolowski verification scales at $\mathcal{O}(\log T)$, whether $T=100,000$ or $T=10,000,000$, the verification time will remain entirely flat at these speeds. This makes it perfectly fast enough for both desktop and mobile web wallets to instantly verify massive blocks without impacting the user experience.

## Cross-Platform Native Benchmarking

To measure the true "speed limit" of your processor without the overhead of the WebAssembly abstraction layer or UI framework FFI bindings (Tauri/Flutter), you can run the pure Rust `native_bench` directly.

### Desktop Native (x86_64 / ARM64)
To test raw performance on your desktop machine:
```bash
cargo run --release --example native_bench
```

**Execution Results:**
```text
Result: ✅ VALID
Total time: 128.61 seconds
Average time per verification: 128.61 ms
(Measured over 1000 runs natively)
```

*Note: Desktop benchmarks were executed on an **11th Gen Intel(R) Core(TM) i5-11400H @ 2.70GHz** processor with 16GB RAM.*

### Mobile Native (Termux / ADB Shell)
To test the raw performance of an Android ARM64 processor without the overhead of Flutter, you can execute the Rust binary directly on the phone (via Termux or ADB).

**1. Termux Execution Results:**
Running the benchmark directly inside Termux on the mobile device over 1,000 runs yielded:
```text
Result: ✅ VALID
Total time: 296.34 seconds
Average time per verification: 296.34 ms
(Measured over 1000 runs natively)
```

**2. Cross-Compiling via ADB (Alternative):**
*(Ensure you have the Android NDK and `cargo-ndk` installed)*
```bash
cargo ndk -t arm64-v8a build --release --example native_bench
adb push target/aarch64-linux-android/release/examples/native_bench /data/local/tmp/
adb shell chmod +x /data/local/tmp/native_bench
adb shell /data/local/tmp/native_bench
```

*Note: The native benchmarks resulting in ~300ms verification times were executed on a **Nothing A059P** smartphone with 8GB RAM. It is powered by a **Qualcomm SM7635 (Snapdragon) Octa-Core Processor** featuring:*
* *- 1x Prime Core @ 2.49 GHz*
* *- 3x Performance Cores @ 2.40 GHz*
* *- 4x Efficiency Cores @ 1.80 GHz*

### Flutter Mobile App (`flutter_bench`)
To measure real-world performance inside a cross-platform mobile app, we executed the exact same $T=100,000$ test vector using the `flutter_rust_bridge` FFI bindings built in release mode on the same device.

```text
Result: ✅ VALID
Total time: 302.73 seconds
Average time per verification: 302.73 ms
(Measured over 1000 runs natively)
```

**FFI Overhead Conclusion:**
The pure ADB shell native execution was **300.67 ms**.
The Flutter Dart-to-Rust bridge execution was **302.73 ms**. 

This proves that integrating `kyn-vdf` into a Flutter app adds a virtually negligible **~2ms** of FFI (Foreign Function Interface) overhead per verification, while maintaining massive performance gains over running in a mobile web browser (~568 ms).

### Tauri Desktop App (`tauri_bench`)
To measure the real-world performance of integrating the Rust cryptography natively into a desktop application (rather than WebAssembly in the browser), we executed the exact same $T=100,000$ test vector using the Tauri IPC backend built in release mode.

```text
Result: ✅ VALID
Total time: 132.28 seconds
Average time per verification: 132.28 ms
(Measured over 1000 runs natively)
```

**Desktop Performance Conclusion:**
The desktop Tauri native execution was **132.28 ms**.
The desktop Chromium WebAssembly execution was **381.56 ms**.

By leveraging Tauri to run `kyn-vdf` directly as a native system binary rather than inside a V8 WebAssembly sandbox, the verification is **nearly 3x faster** on the exact same Intel i5 processor. This solidly justifies the use of native desktop application wrappers over standard web clients for heavy cryptography!
